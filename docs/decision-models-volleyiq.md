# Jev 式決策模型與 VolleyIQ 整合構想

整理日期：2026-09-19。

本文件整理 Jev、Decider-2B、context 篩選與 VolleyIQ 的產品討論。外部模型資訊來自文末資料來源；VolleyIQ 現況來自整理當日的程式碼。整合方案、產品效果與實驗設計皆為提案，尚未實作或驗證，不代表模型已具備排球分析能力。

## 1. 核心判斷

Jev 式模型適合把「規則難以寫清楚的小判斷」變成程式能直接使用的選項或機率。對 VolleyIQ 最值得驗證的用途，是根據球員的複盤目標選片、安排人工確認，以及長期整理可比較的比賽證據。

產品突破的假設是：讓使用者從「自己找影片」進一步走到「打完球就知道值得看哪幾球」。模型只是其中一個元件；真正需要累積的是影片證據、球員目標、專業判斷與使用者回饋。

目前建議的第一個實驗是「五球複盤」，先與純規則選片比較，再決定是否值得整合模型。沿用現有可運作的視覺分析流程，從一個完整、範圍小的功能開始。

## 2. Jev 是什麼、輸入是什麼

TypeSafe AI 將 Jev 稱為 System One 模型。它接收資料與型別化問題，直接回傳決策結果，不需要逐 token 產生一段回答，再由程式解析。

核心輸入是：

- `state`：被判斷的內容與相關背景。
- `questions`：一個或多個具名問題。
- 每個問題的 `instructions`：自然語言描述的判斷目標。
- `criteria`：選項及定義，或評分的級別描述。

原生 API 的三種問題是：

| 類型 | 用途 | 主要輸出 |
| --- | --- | --- |
| Choice | 從給定選項中選擇 | 選項、機率分布、confidence |
| Score | 根據有序級別評分 | 分數、機率分布、confidence |
| Noul | 判斷命題是否成立 | 0–1 的成立機率 |

Noul 不是直接回傳確定的 true/false。採取動作的門檻需要在程式中定義，並用實際任務資料驗證。多題可在同一次請求中評估，各題不應依賴同一次請求中另一題的答案。

輸出符合 schema，不代表內容正確。把複雜推理改寫成選擇題，也不會讓任務自動變簡單。明確的計數、時間比較、條件篩選與統計應交給程式。

來源：[TypeSafe Introduction](https://docs.typesafe.ai/introduction)、[Quick start](https://docs.typesafe.ai/introduction/quickstart)。

## 3. 訓練公開程度與開放模型

### Jev

官方稱訓練方法為 Reinforcement Learning for Calibrated Decisions（RLCD），目標包含決策機率的校準。本次查閱的公開資料沒有足以完整重現的訓練配方、資料集與獎勵函數。

「校準」描述大量預測的統計性質：例如給出約 80% 機率的事件，在相應評估群體中應約有 80% 成立。它不是對單一判斷正確性的保證，也不能假設會自動泛化到排球領域。

### 可研究的開放方案

| 模型／專案 | 方向 | 公開內容與限制 |
| --- | --- | --- |
| [Decider-2B](https://huggingface.co/Mapika/decider-2b) | 通用文字決策，從候選答案輸出機率 | 模型卡標示 Apache-2.0；公開權重與訓練方式，不能視為 Jev 等效替代品 |
| [NanoJev](https://github.com/TianyuCodings/NanoJev) | 0.6B 平行決策模型 | 公開權重、資料與訓練流程；展示集中於遊戲與局部決策 |
| [LLMLingua-2](https://github.com/microsoft/LLMLingua) | prompt／context 壓縮 | 公開模型與訓練流程；是較專門的壓縮工具，不是通用決策模型 |

Decider-2B 的模型卡描述：以 Qwen3.5-2B-Base 為基底，把分類、相關性、工具選擇等資料整理為 context、問題及選項，以交叉熵做全參數微調。推論時讀取答案位置的候選分數並轉成機率，省去逐字解碼；後續版本加入 Agent 軌跡、網頁元素選擇與遊戲狀態資料。

這提供一條監督式訓練路徑，不需要先重現 TypeSafe 未公開的 RLCD。模型卡的評測主要是作者自評；尚未證明它適合長篇 coding context 刪減或排球複盤。實驗應固定權重 revision，避免模型更新造成比較失真。

## 4. 兩個應用範例帶來的啟發

### browser-use/jev-ultrafast

這是一個應用程式專案，不是另一個模型。其流程是：

```text
自然語言目標＋網頁 DOM 元素列表
  → Jev 選操作與目標元素
  → 需要輸入文字時，另一個文字模型產生內容
  → 程式操作瀏覽器
  → 重新觀察
```

查閱時預設決策模型為 TypeSafe 的 `jev-latest`，文字模型為透過 OpenRouter 呼叫的 Inception Mercury 2.5。Jev 不直接操作 Chrome；程式負責執行動作。網頁狀態被動態轉成選擇題，不需要替每個網站另訓練模型。

對 VolleyIQ 的啟發是：先由專用系統取得可用證據，再把範圍明確的選擇交給決策模型，最後由程式執行與驗證。

來源：[jev-ultrafast](https://github.com/browser-use/jev-ultrafast)。

### fast-jev-compaction

這個專案使用現成 Jev，詢問工具呼叫及其結果是否需要保留，再依門檻保留、截短或移除，並沒有額外訓練 context 模型。

重要的資料流差異：呼叫遠端 Jev，仍會把供判斷的 context 傳到 TypeSafe。節省的是後續主模型讀取的內容，並不是讓資料留在本機。

查閱時的實作會先把工具結果原文換成簡短註記，並按長度上限截短其他內容；因此不是完整原文全數外送，也不是 Jev 一定能看到被刪結果的內容。問題分批時，會重送同一份整理後的 state。

這也限制判斷品質：「與目前問題相關」比「未來一定用不到」容易定義。若採本機開放模型，可避免送往 TypeSafe，但仍要負擔本機推論成本，並測試錯刪關鍵資料的風險。

來源：[fast-jev-compaction](https://github.com/tamaratran/fast-jev-compaction#how-it-works)。

## 5. VolleyIQ 已有的基礎與能力邊界

整理當日可從程式確認的基礎：

| 現有資料／流程 | 可支援的用途 |
| --- | --- |
| 回合起訖、winner 欄位 | 回合切片與已辨識勝方資訊；winner 可能未知 |
| 動作事件 ID、label、time、frame、可選 xy | 依動作與時間建立候選片段、回到原影片 |
| 球員辨識與人工歸屬修正 | 依已確認球員整理片段 |
| 人工 result、lossReason、tag、trim、移除紀錄 | 建立使用者確認資料與後續評估材料 |
| 分離保存模型輸出與人工修正 | 新分析結果不必覆蓋使用者判斷 |

程式來源：

- [Detector contract](../src/yp_video/contracts/detector.py)
- [ActionAnnotation](../../VolleyIQ/VolleyIQ/Models/ActionAnnotation.swift)
- [MatchCorrections](../../VolleyIQ/VolleyIQ/Models/MatchCorrections.swift)
- [現有 app 流程](../../VolleyIQ/README.md)

目前的公開事件 contract 不包含完整的動作品質、球路、姿勢、戰術情境或事件置信度。人工失分原因欄位存在，也不表示每個片段都有標註。

例如 `receive → set → spike → 失分` 不能直接證明「接發不好導致失分」。文字模型只能使用輸入中的證據，不能憑空補出影片裡尚未被感知模型擷取的資訊。球員外觀辨識繼續由視覺模型處理。

## 6. 三個產品方向

### 第一層：五球複盤

**目標：** 使用者選定複盤主題後，直接取得少量值得回看的片段。

以「今天看我的接發球」為例：

1. 程式依已確認的球員、動作與比賽範圍篩出候選。
2. 整理每段的事件、已有人工標記、相鄰事件與來源時間。
3. 有足夠語意證據時，決策模型評估與目標的相關性及候選分類。
4. 程式限制數量、去除重複，組成具有多樣性的複盤片段。
5. 每張卡片連回影片，呈現已有證據與一個明確觀察問題。

初版不需要生成長篇教練建議。只有成功／失敗等標記確實存在時，才用於分類；缺少資料時呈現待確認，不把未知當成失敗。

若輸入只有球員、動作和時間，且使用者目標也只是固定類別，純規則可能已經足夠。決策模型必須在更模糊的相關性或多樣性需求上證明額外價值。

### 第二層：用最少確認改善最多片段

**目標：** 優先請使用者確認對整體結果最有幫助的項目。

例：一個尚未對應球衣號碼的辨識群組涉及很多次觸球，優先確認它，可以一次改善多個個人片段的歸屬。

先以事件數量、現有辨識不確定性和已確認狀態建立規則基準；只有額外的語意判斷確實有用時，才加入決策模型。核心指標是每分鐘人工確認能改善多少片段，而不是模型呼叫次數。

### 第三層：有影片證據的個人進步追蹤

**目標：** 依球員的長期目標，持續整理可比較的片段與已確認結果。

例：「改善接發穩定性」可以先做跨比賽的相似案例比較。決策模型選擇符合目標且條件接近的候選；程式計算數量與統計；進一步的動作解讀需要額外視覺證據和專業標註。

此方向依賴可靠的跨比賽球員對應、可比較的情境資料、足夠標註與樣本量。不能把少數片段的選取差異直接當成能力進步，也不能只比較勝負就推導技術改善。

## 7. 整合方式與職責

```text
影片
  ↓
現有視覺 pipeline：回合、動作、人物、球員辨識
  ↓
事件資料＋人工修正＋使用者複盤目標
  ↓
程式建立候選與證據
  ↓
決策模型：相關性、候選分類、是否有足夠資訊
  ↓
程式：選片、統計、結果驗證
  ↓
App：影片證據＋使用者回饋
```

- 視覺 pipeline 負責影片感知；決策模型不替代 SPOT、actor 或 ReID。
- 計數、明確條件、時間窗與選片數量由程式決定。
- 決策結果保留來源 event ID、模型 revision 與問題版本，方便回到證據和重現實驗。
- 未確認的模型建議與人工修正分開保存，不能直接寫成 ground truth。
- 不把整場影片或所有歷史轉成超長文字；先依任務建立必要候選與局部證據。
- 第一個離線實驗只需要一個資料匯出與評估入口，不先建通用 Agent 框架、多供應商相容層或插件系統。

部署可先評估現有自架 GPU 上的 Decider-2B。這代表資料留在 VolleyIQ 控制的伺服器，不等於留在使用者手機。需測量與既有視覺工作的 GPU 競爭、顯存與延遲；不先承諾即時推論或手機端運行。

遠端 API 則按使用量計費。討論時 Jev 官網列每十億輸入 tokens 42 美元；Mercury 的 OpenRouter 頁面有促銷價格。這些不是固定成本承諾，正式估算前應重新核對定價。省去文字解碼也不代表讀取長輸入沒有成本。

## 8. 最小實驗與進入產品的條件

第一個實驗固定為「五球複盤」，先選一個有足夠標註的動作主題。

1. 凍結比賽清單、候選片段、可用標註與複盤目標。
2. 建立純規則基準，再以完全相同候選與輸入評估 Decider-2B。
3. 請球員或教練盲評兩組選片，記錄有用性、遺漏的重要片段與不被證據支持的分類。
4. 測量找片時間、選片多樣性、推論時間與資源成本。
5. 只有在使用者價值改善且成本可接受時，才串到正式 UI。

決策品質與最終選片品質分開量測。若機率用於自動採納或要求確認，另外檢查任務內的校準與不同門檻下的誤判；不能直接沿用通用模型的 confidence 宣稱。

資料以整場比賽分組切分，避免相鄰回合或同一影片跨 train／validation；若主張跨球隊或跨球員泛化，還需要相應的保留測試組。所有模型只能看到實際產品執行時可取得的資料。

## 9. 後續訓練資料的形成

若實驗證明有價值，可以累積排球專用的決策樣本：

```text
輸入：複盤目標＋片段證據＋問題＋候選答案
標註：人工確認答案／選片偏好／資訊不足
來源：比賽、回合、event ID、影片時間、標註版本
```

現有 corrections 是起點，但不是完整的決策訓練集：

- 沒有修改不代表同意模型，也不能當作負樣本。
- 收藏或移除可能反映個人偏好，不一定是動作正誤。
- 球員歸屬修正不能直接當作技術品質標籤。
- 「資訊不足」應是明確可標註的情況，避免迫使模型猜測。
- 第一階段收集的應是與產品目標對應的人工判斷，而不是讓模型自產標籤後宣稱準確度提升。

待資料足夠，再比較通用模型、排球微調模型與簡單分類器。採取能完整滿足需求的最簡方案，模型複雜度本身不是產品成果。
